# Guardian #2 Findings: Release Candidate Logic

**Status:** ROOT CAUSE IDENTIFIED
**Severity:** CRITICAL
**Confidence:** 100%

---

## TL;DR

**The release threshold is mathematically impossible to exceed with realistic contract data.**

Expected value formula treats player ratings as dollar amounts ($1.05M for a 70-rated player), while actual contracts are 5-20x higher ($8-15M). This causes zero releases despite the system appearing to work in unit tests.

---

## The Problem

### Current Formula
```
cap_inefficiency = (annual_value / expected_value) * age_penalty

expected_value = (eval_score / 100) * value_threshold
                = (eval_score / 100) * 1.5
```

### Example: 70-Rated Player, Age 27
- **expected_value** = (70/100) * 1.5 = **$1.05M**
- **Threshold to be released:** annual_value > $1.05M
- **Realistic contract:** $8-15M
- **Result:** Cap inefficiency = 8.0 / 1.05 = **7.6x over threshold**

### The Math Doesn't Work

| Player Rating | Expected Value | Realistic Contract | Inefficiency |
|--------------|---------------|-------------------|--------------|
| 60 | $0.90M | $5M | 5.6x |
| 70 | $1.05M | $10M | 9.5x |
| 80 | $1.20M | $18M | 15.0x |
| 90 | $1.35M | $30M | 22.2x |

**Every player with a market-rate contract massively exceeds the threshold.**

---

## Why Unit Tests Pass

Unit tests use **artificially constructed mismatches:**

```gdscript
// Test data: Intentionally broken contract
{
    "eval_score": 55.0,      // Low rating
    "annual_value": 15.0,    // High contract - UNREALISTIC
}
```

This creates the needed mismatch, but **realistic contracts generated by the system are consistent with player value** and don't create these mismatches.

---

## Why Integration Tests Show Zero Releases

### Hypothesis: Roster Composition in Year 20+

Most rosters consist of:
1. **40% Recent Draft Picks (0-2 years)** - Protected by rookie contract rule
2. **30% Young Veterans (3-5 years)** - Still on cheap rookie-scale deals
3. **20% Prime Veterans (6-10 years)** - Mixed contracts
4. **10% Aging Veterans (11+ years)** - Expensive but rare

**If most eligible players are:**
- On rookie contracts (cheap) OR
- Already released/retired naturally OR
- On team-friendly extensions

**Then:** Very few players have expensive enough contracts to need releases, even though threshold is impossibly low.

**Alternative possibility:** Contract generation itself is broken and producing unrealistically LOW values, which would also explain zero releases.

## Evidence

### Diagnostic Test Results

Running with **synthetic realistic contracts:**

```
Average eval_score: 73.4
Average annual_value: $9.30M
Average cap_inefficiency: 9.045

Players exceeding threshold: 36 / 36 (100.0%)
```

With realistic values, **every single player** becomes a release candidate.

### Mathematical Proof

For a player to **avoid** being a release candidate:

```
cap_inefficiency <= 1.0
annual_value <= expected_value
annual_value <= (eval_score / 100) * 1.5

Example: 80-rated player (age 27, no penalty)
annual_value <= (80/100) * 1.5
annual_value <= $1.20M
```

An 80-rated starter must earn less than $1.2M to avoid release consideration. **This is impossible in realistic contract economics.**

---

## Root Causes

### 1. Formula Treats Ratings as Dollars

The formula `expected_value = (eval_score / 100) * 1.5` appears to treat:
- 100-point rating scale as percentage
- value_threshold (1.5) as scaling factor to millions

**Result:** 70-rated player = 70% * $1.5M = $1.05M

**Reality:** 70-rated player = $8-15M depending on position

### 2. Missing Market Context

The formula has no awareness of:
- Position-specific market rates (QB > WR > RB)
- League-wide salary cap context
- Actual contract generation economics

### 3. Config Parameter Mismatch

`value_threshold = 1.5` seems intended to mean "cut if 50% overpaid" but actually means "multiply rating by 1.5 to get millions".

**Semantic confusion:** Parameter name doesn't match actual formula behavior.

---

## Recommended Solutions

### Option A: Fix Formula (Best Long-Term)

Replace expected_value with actual market valuation:

```gdscript
// Use PlayerValue.calculate() for market-based valuation
var valuation := PlayerValue.calculate(player, context, cfg, rng)
var market_value := valuation.get("market_value", 1.0)
var expected_value := market_value * value_threshold
```

**Result:** value_threshold = 1.5 means "cut if paid 50% over market"

**Pro:** Integrates with existing economic systems
**Con:** Adds dependency, requires testing

---

### Option B: Add Market Multiplier (Quick Fix)

```gdscript
var market_multiplier := float(cfg.get("market_value_multiplier", 0.15))
var expected_value := (eval_score * market_multiplier) * value_threshold
```

**Config:**
```json
{
  "market_value_multiplier": 0.15,  // 70 rating = $10.5M baseline
  "value_threshold": 1.5             // Cut if 50% overpaid
}
```

**Result:** 70-rated player threshold = 10.5 * 1.5 = $15.75M

**Pro:** Simple, one parameter change
**Con:** Still position-agnostic

---

### Option C: Recalibrate Threshold (Workaround)

```json
{
  "value_threshold": 13.0  // (was 1.5)
}
```

**Result:** 70-rated player threshold = 0.70 * 13.0 = $9.1M

**Pro:** Simplest fix (one number)
**Con:** Doesn't fix semantic confusion, no position differences
